# NAJAT360 Companion

A synthetic-data-only companion layer for emergency dispatch operations,
built for a hackathon submission. **This project is not affiliated with,
integrated into, or derived from any real CAD/dispatch system's code or
data.** Every row in its database is marked `synthetic: true` and is
generated by `scripts/seed-demo.ts`; there is no live connection to any
external platform anywhere in this codebase (see
`docs/integrations/cad-read-provider.md`).

## What this is

NAJAT360 explores how AI-assisted intake, coverage-aware unit dispatch,
and a field-crew "where do I stop / which entrance / how far" card could
work on top of an emergency dispatch workflow — as a demonstration, not a
replacement for or modification of any production system. The product
rationale and phased build plan live in `docs/product/`.

## Status

**Phases C1–C6** — core schema, RBAC, incident state machine, the
AI-output allowlist boundary, the synthetic CAD provider, location
fusion/conflict handling, coverage-aware Dispatch Score, plus a **live
Next.js web application** covering the full P0 golden path end to end:
caller intake (QR Rescue Anchor scan or GPS) → call-taker location
confirmation, on a live map showing the fused location, uncertainty
radius, and every raw observation → supervisor coverage-aware dispatch
decision, with the recommended unit/entrance plotted on the same map →
medic FieldLink through closure. See `docs/product/NAJAT360-قرارات-ما-بعد-C0.md`
for the phase gate list (C0–C9) and what is deliberately deferred to
later phases; C7–C9 (hospital handover, alerting, replay/export) are not
built yet.

## Getting started

```bash
npm install
cp .env.example .env   # DATABASE_URL etc — nothing in .env.example is a real secret
```

You need a local Postgres instance. This sandbox environment could not run
`prisma generate`/`prisma migrate` (network egress to `binaries.prisma.sh`
was blocked — see `prisma/migrations/0001_init/migration.sql`'s header
comment), so the schema was applied by hand:

```bash
for d in prisma/migrations/*/; do psql "$DATABASE_URL" -f "$d/migration.sql"; done
# applies, in order: 0001_init, 0002_c3_location, 0003_c4_dispatch,
# 0004_c5_fieldlink, 0005_c6_coverage
```

On a machine with normal internet access, reconcile those migrations
properly and generate the Prisma client instead:

```bash
npm run prisma:generate
npm run prisma:migrate
```

Then seed deterministic demo data and run the checks:

```bash
npm run seed        # idempotent — safe to re-run; ~2000 historical incidents by default
                     # (override with SEED_HISTORICAL_COUNT=50 for a fast local reseed)
npm run verify       # typecheck + lint + secret scan + phase-gate scan + tests
```

## Running the web app

```bash
npm run dev          # http://localhost:3000
```

Make sure `.env` has `DEMO_MODE=true` (the default in `.env.example`) — it
gates the Demo Role Switcher and the `/api/demo/reset` endpoint (see
`src/lib/demo-mode.ts`). With `DEMO_MODE` unset/false, both are
structurally disabled — not hidden, disabled — which is the intended
behavior for any non-demo deployment.

**Walking the golden path solo** (one browser tab, using the role
switcher in the header):

1. Open `/anchors`, note a Rescue Anchor code (or just open `/caller` and
   use the "GPS" location option instead — no anchor needed).
2. Open `/caller`, submit a report. You get a rescue code and the caller
   screen starts polling its own status.
3. Switch the header role to **مستقبل البلاغ / CALL_TAKER**, open
   `/operations`, select the new incident, optionally add another
   observation, then **confirm the location**.
4. Switch the header role to **المشرف / SUPERVISOR**, on the same incident
   **generate a recommendation** (shows the top pick vs. alternative and
   coverage before/after), then **confirm the dispatch**.
5. Switch the header role to **المسعف / MEDIC**, pick the unit that was
   just dispatched, and step it through Accept → Start moving → At access
   point → On scene → Close — the caller screen's status updates the whole
   way (poll every 5s).
6. `/` has a **demo reset** button (`POST /api/demo/reset`, optionally
   `?fast=1` for a ~50-row reseed) to wipe every incident this walkthrough
   created and re-seed the full known-good fixture set before a fresh run.

## Deploying for free

Nothing in this stack requires a paid subscription:

- **App hosting**: [Vercel](https://vercel.com)'s free tier runs Next.js
  App Router route handlers natively — `vercel deploy` after setting the
  env vars below in the project's dashboard.
- **Postgres**: any free-tier managed Postgres (e.g. Neon, Supabase,
  Railway's free tier) works — this app only needs a connection string, no
  Postgres extensions beyond what a stock instance ships with.
- **Routing/ETA**: `ROUTING_PROVIDER=mock` (the default) needs no API key
  at all — see `src/lib/routing/mock-provider.ts`'s header for exactly what
  it estimates and how, and `docs/` for the optional paid-provider adapter
  interface this is designed to swap behind later, off by default.

Minimum env vars for a deployment: `DATABASE_URL`, `DEMO_MODE=true` (for a
hackathon demo; `false`/unset for anything else), `APP_URL`,
`ROUTING_PROVIDER=mock`.

### A known, intentional tradeoff: Next.js 14, not 16

This app is built on Next.js 14.2.35 / React 18, not the current Next 16 /
React 19. `npm audit` flags several high/critical CVEs in this exact Next
14.2.35 version — all in subsystems this app does not use (the image
optimizer, i18n rewrites, middleware matchers, server actions/websockets
internals). The decision to stay on 14 rather than migrate to 16 under
hackathon time pressure was made explicitly, not silently: a major-version
Next.js migration this close to a submission deadline is a bigger risk to
the working demo than these specific, unused-surface CVEs. This mirrors
the project's own master spec, which already frames this codebase as "a
hackathon version, not final security certification." A production
deployment beyond the hackathon should upgrade to a patched Next.js
version first.

## Why some things look unusual for a Next.js project

This repo was built inside a sandboxed cloud environment with restricted
network egress, which blocked the Prisma CLI's binary download. Rather
than silently working around that in a way a reader couldn't see, every
place it mattered has a comment explaining the deviation and what running
it in a normal environment would do differently — start with
`prisma/schema.prisma`'s header and `src/lib/domain/types.ts`'s header.

The same sandbox also has no egress to `tile.openstreetmap.org`, so the
operations screen's live map (`app/_components/IncidentMap.tsx`) renders
its markers, uncertainty-radius circle, and unit/entrance/route line
correctly, but the background map tiles themselves don't load in
screenshots taken from this environment — a network restriction of this
sandbox, not a bug in the map code. Any normal hosting environment
(Vercel included) reaches OpenStreetMap's public tile server with no
code changes required.
